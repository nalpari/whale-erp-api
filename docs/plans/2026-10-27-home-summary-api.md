# 로그인 후 홈 집계 API (WHALEERP-305 · 306)

관리자 웹 로그인 후 홈의 수치 카드 · 점포별 현황 표 · 처리 대기 · 경고 밴드에 쓰는 집계 API 두 개를 만든다.
화면은 front PR(WHALEERP-307~310)이, 점포 하나 화면은 그다음 PR(WHALEERP-341 · 342 · 344)이 맡는다.

- 기준: Manyfast 「홈 현황 요약과 처리 대기」, 운영 정책 HOM-01~08(v211) · CTR-29 · ATT-30 · JOI-08
- 목업: whale-erp-front `docs/mockup/home/signed-in.html`
- 작업 지시: 기획 세션 24, 2026-10-27 재영 「로그인 후 홈 작업 시작하자, 점포 하나도 묶어서」

## 정한 것 (2026-10-27 재영)

| 물음 | 결정 |
|---|---|
| PR 나누기 | 셋 — ① 이 api 집계 ② front 여러 점포 화면 ③ 점포 하나 화면 api+front |
| 플랫폼 계정(PM · PA)의 홈 | 현황 없이 안내만. 이 API 는 플랫폼 계정에 403 이 아니라 빈 결과(`platform: true`)를 준다 |
| 「내 문의」 | 로그인한 관리자가 쓴 문의만 센다 |
| 처리 대기의 문의 줄 | 내가 쓴 답변완료 문의 중 **마지막 답변**이 최근 7일 안인 것(첫 답변 아님, api #166 리뷰). 읽음 표시 칸은 두지 않는다 |
| 처리 대기의 소속 확인 거절 | 그 직원 레코드의 마지막 초대가 거절(소속 추가 확인 · 복귀 확인)이고 그 뒤 새 진행(재발송 · 새 계약 · 퇴직 처리)이 없는 동안 센다 |

Plane 설명에 남은 「연결 확인 필요」 · 「가입자 연결 확인 필요」는 연결 보류를 없애며 빠졌다(운영 정책 HOM-03 · JOI-06, 2026-10-19).
근로계약 수정 요청은 미조치와 처리 대기 계약에 들어간다(HOM-03 · 07).

## 업무 범위

- 관리 범위는 `AdminScopeService.getManageableStores` 다(직원 · 근로계약 · TO-DO · 급여명세서 목록과 같다).
- 업무 범위는 front 헤더 범위 선택기가 정한다(`?scope=` · sessionStorage). front 가 범위를 점포 ID 로 풀어
  `storeIds` 로 보낸다(다른 목록과 같은 방식). 없으면 관리 범위 전체다. 관리 범위 밖 ID 는 조용히 뺀다.
  폐점 점포도 여기서 빼고, 남은 점포로 카드 · 표 · 처리 대기 · 경고 밴드를 모두 센다(합계가 맞고 처리 대기가 표에 없는 점포로 가지 않게, api #166 리뷰).
- 범위를 바꾸면 front 가 다시 부른다(HOM-01). 저장하지 않고 부를 때마다 센다. 응답에 `asOf`(조회 시각)를 담는다.
- 본사 역할(BM · BA)의 ATT-30 가림(운영 정책 ATT-30 v216, 2026-10-27 재영): 가려지는 점포(직영이 아닌 점포)에서는 근로계약 목록과
  같은 조건(`staffMember: HQ_SHARING_CONSENTED`)을 계약 집계(미체결 · 서명 대기 · 수정 요청, 경과 일수 포함) · 갱신 예정(경고 밴드) ·
  소속 확인 거절 · 정직원/파트 나눔에 건다. 미조치 · 점포별 표의 미체결 · 미조치도 같은 집계라 합계가 맞는다. 재직 직원 총수만 그대로
  센다(점포별 숫자). 처리 대기의 직원 이름은 그래도 `hidesPersonalData` 로 한 번 더 본다.

## 권한

- 경로 `/home` 은 메뉴가 아니다. 관리자 토큰이면 부를 수 있고, 영역마다 그 메뉴의 조회 권한이 있을 때만 그 영역을 채운다
  (`adminHasMenuAction` · 직원 상세 요약과 같은 생각). 권한이 없는 영역은 `null` 로 준다 — 403 으로 홈 전체를 막지 않는다.
  - 재직 직원 카드 · 표의 재직 직원 칸: 직원 정보 관리 `/staff-members`
  - 미체결 계약 · 처리 대기 계약 · 경고 밴드: 근로계약 관리 `/contracts`
  - 오늘 출근: 출퇴근 현황 메뉴(메뉴 url 은 구현 때 마이그레이션에서 확인)와 근무스케줄 `/work-schedules`
  - 내 문의 · 처리 대기 문의: 문의사항 `/support-inquiries`
  - 처리 대기 소속 확인 거절: 직원 정보 관리 `/staff-members`
  - 처리 대기 긴급 TO-DO: TO-DO `/todos`
- 미조치(HOM-03)는 볼 수 있는 영역의 건수만 더한다.

## 세는 법

- **재직 직원**(HOM-02 · CTR-29): 퇴직 처리되지 않은 직원 레코드. 임시저장 계약만 있는 레코드는 뺀다. 고용 형태별(정직원 · 파트타이머)로 나눈다.
- **미체결 계약**: 발송 대기 · 서명 대기 · 수정 요청.
- **운영 점포**: 범위 안 폐점이 아닌 점포. 직영 · 가맹으로 나눈다.
- **오늘 출근**(한국 날짜, `kstToday`): 근무 예정 = 그날 근무스케줄이 있는 재직 직원 수, 출근 = 그날 출근 기록이 있는 직원 수,
  미출근 = 근무 예정인데 그날 첫 근무의 시작 시각이 지났고 출근 기록이 없는 수(시작 전은 세지 않는다, 운영 정책 ATT-34).
- **미조치**(HOM-03): 점포별 서명 대기 계약 + 근로계약 수정 요청 + 소속 확인 거절 + 긴급 TO-DO 미완료.
- **점포별 현황 표**(HOM-06): 점포마다 재직 직원 · 미체결 계약 · 오늘 출근(출근 / 근무 예정) · 미조치. 미조치 많은 순(같으면 점포명)
  일곱 곳과 전체 점포 수를 준다.
- **경고 밴드**(HOM-04): 갱신 예정 계약 중 종료일이 오늘부터 7일 안인 것. 갱신 예정의 대상 규칙은 하루 배치(`contract-expiry.service`)와
  같다 — 체결 완료, 같은 직원에게 진행 중인 다른 계약이 없음, 퇴직 처리되지 않음.
- **처리 대기**(HOM-07): 건수가 0인 유형은 뺀다. 순서는 경고 밴드 대상(계약 갱신 예정) → 계약(서명 대기 · 수정 요청) → 직원(소속 확인 거절)
  → 문의(마지막 답변이 최근 7일 안) → TO-DO(긴급 미완료). 유형마다 건수 · 대표 이름(첫 사람 외 N명) · 가장 오래 기다린 일수(서명 대기는 발송 뒤
  경과 일수) · 이동할 화면의 조건(점포 · 상태)을 준다. 운영 알림은 나열하지 않는다(HOM-08).

## API

- `GET /home/summary?storeIds=1,2` — 수치 카드 넷 · 점포별 현황 표(일곱 곳 + 전체 수) · `asOf`
- `GET /home/pending?storeIds=1,2` — 경고 밴드 대상 · 처리 대기 유형 목록 · `asOf`
- 둘로 나눈 것은 카드 · 표와 처리 대기를 화면이 따로 그리고, 한쪽이 실패해도 다른 쪽은 보이게 하려는 것이다.

## 확인

  권한 없는 영역 null, 본사 역할 가림(동의한 직원만 · 총수는 그대로), 폐점 점포 제외, 미출근의 시작 시각, 플랫폼 계정 빈 결과, 처리 대기 순서 · 0건 유형 숨김, 소속 확인 거절의 「새 진행」 판정,
  문의 7일 경계, 경고 밴드 7일 경계(한국 날짜).
