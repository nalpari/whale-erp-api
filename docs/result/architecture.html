요청 한 번의 경로

가드가 전역이라, 컨트롤러는 파일을 만드는 순간 보호된다. 뚫려 있는 곳은 표시해 둔 곳뿐이다.

기본값이 “인증 필요”이고 예외만 표시한다. 반대로 두면 라우트를 추가할 때마다 보호를 빠뜨릴 수 있고, 빠뜨린 것은 사고가 나기 전까지 보이지 않는다.

@UserTypes 는 허용 목록이 있으면 그 목록이 전부다. 인자를 빠뜨린 @UserTypes() 는 전원 거부이지, 전원 허용이 아니다 — 제한을 거는 모양의 데코레이터가 조용히 아무것도 하지 않는 상태가 되면 안 된다. ItemsController 가 @UserTypes('staff') 로 좁혀 두지 않았다면 고객 토큰으로도 품목 마스터를 지울 수 있다.

요청 제한은 /auth 에만 건다. 토큰 없이 두드릴 수 있는 표면이 거기뿐이고, 축이 둘인 이유는 하나로는 못 막기 때문이다 — IP 축만 두면 봇넷이 한 계정을 나눠 두드리는 것을, 계정 축만 두면 한 호스트가 이메일을 갈아 가며 CPU 를 태우는 것을 놓친다.

리프레시 회전

세션은 사용자 행에 저장된 해시 하나다. 회전의 판정은 조건부 updateMany 한 문장 안에서 끝난다.

0행이 돌아왔다는 것은 제시된 토큰이 이미 소비됐다는 뜻이고, 그것이 탈취된 옛 토큰의 재사용인지 동시 요청 중 진 쪽인지는 서버가 구분할 수 없다. 전자가 도난 신호이므로 안전한 쪽 — 세션 종료 — 으로 끊는다. 대가는 명확하다: 갱신을 동시에 두 번 쏘는 클라이언트는 스스로를 로그아웃시킨다.

토큰마다 jti 를 넣는 것은 장식이 아니다. 없으면 같은 초에 두 번 발급한 토큰이 바이트 단위로 같아져, 회전이 아무것도 회전시키지 못하고 직전 토큰이 계속 통과한다.

부팅 시 구성

값 하나가 비면 서버는 기본값으로 도는 대신 뜨지 않는다. 이건 설정이 아니라 설계다.

HS256 은 한 바이트짜리 키로도 군말 없이 서명한다. 길이 검사를 빼면 캡처한 토큰 하나로 키를 깰 수 있고, 그렇게 위조한 것은 staff 토큰이다. 추측 가능한 키로 뜬 서버보다 못 뜨는 서버가 낫다 — 기본값을 만들지 않는 이유다.

데이터

신원 테이블은 하나가 아니라 둘이다. 컬럼이 같아서 코드 경로는 하나로 유지된다.

주의할 곳 둘. CHECK 제약은 db:pull 에서 살아남지 못한다 — Prisma 스키마 언어가 표현하지 못해 introspection 이 조용히 지우므로, 마이그레이션 SQL 이 유일한 원본이다. 그리고 id 는 integer 라, 2147483647 을 넘는 경로 파라미터는 DB 에 닿기 전에 걸러야 한다. 그냥 보내면 404 여야 할 것이 500 이 된다.

아직 없는 것

지금 구조가 감당하지 못하는 지점과, 그때 가서 무엇을 하면 되는지.

  • 단일 세션리프레시 해시를 사용자 행에 직접 둔다. 계정당 유효한 토큰이 하나뿐이라 다른 기기에서 로그인하면 이전 기기의 갱신이 끊긴다. 다중 기기가 필요해지면 refresh_tokens 테이블로 분리한다.
  • 동시 갱신같은 토큰으로 두 번 쏘면 진 쪽이 세션을 끊는다. 서버에서 재사용과 경쟁을 구분하려면 토큰 계열(family) 추적이 필요하다. 지금은 갱신 직렬화가 클라이언트 몫이다.
  • 요청 한도 저장소카운트가 프로세스 메모리에 있다. 인스턴스를 두 대로 늘리면 실효 한도도 두 배가 된다. 그때 공용 저장소(Redis)로 옮긴다.
  • 가입 엔드포인트없다. 계정은 pnpm user:create <staff|customer> <email> <name> 로만 만들고, upsert 라 비밀번호 재설정도 겸한다. 비밀번호는 인자가 아니라 프롬프트로 받는다 — argv 는 셸 히스토리와 ps 와 CI 로그에 남는다.
  • 남은 스캐폴드AppController 가 / 에서 아직 "Hello World!" 를 돌려준다. 실제 라우트가 그 자리를 대신하면 지운다.
